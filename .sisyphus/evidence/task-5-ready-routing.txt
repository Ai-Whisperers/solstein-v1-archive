# QA Scenario 1: GET /health/ready vs GET /ready — Routing Conflict
# Date: 2026-02-26
# Status: PASS

## Verification Method: Code Analysis (not live server)

### Step 1: Confirm /ready exists in TWO routers

enrichment.py (line 213):
  @router.get("/ready", response_model=ReadinessCheckResponse)
  → Registered in main.py line 132: app.include_router(enrichment.router) [no prefix]
  → Final path: GET /ready

health.py (line 50):
  @router.get("/ready", name="readiness_check")
  → Router has prefix="/health" (line 18)
  → Registered in main.py line 133: app.include_router(health.router) [no additional prefix]
  → Final path: GET /health/ready

### Step 2: Determine which router serves each path

From main.py router registration order:
  Line 132: app.include_router(enrichment.router)    # FIRST — registers /ready
  Line 133: app.include_router(health.router)         # SECOND — registers /health/ready

FastAPI resolution:
  GET /ready       → enrichment.py (first registered, wins)
  GET /health/ready → health.py (unique path, no conflict)

### Step 3: Both return similar readiness status

enrichment.py /ready response:
  {"ready": true, "timestamp": "...", "checks": {...}}

health.py /health/ready response:
  {"ready": true, "timestamp": "..."}

Both check readiness but enrichment.py includes more detailed checks (configuration, connectors, cache, enrichment_enabled, database_ready).

### Step 4: Documentation accurately reflects this

Documentation includes:
- ⚠️ Warning on /health/ready about dual implementation
- Dedicated "Routing Conflict: /ready and /health" section
- Table showing which router wins for each path
