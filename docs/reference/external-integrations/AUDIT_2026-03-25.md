# External Integration Audit

Date: `2026-03-25`

## Scope

This audit separates four things that had been mixed together:

- live pipeline dependencies
- optional but real lookup/search dependencies
- present connector modules whose runtime role is not primary
- prospective providers documented in setup docs but not yet integrated end-to-end

## First Findings

1. The repo does not have a single, stable external-integration contract index.
   `docs/API_PROVIDERS_GUIDE.md` is useful for onboarding, but it is mostly key-acquisition guidance rather than contract and caveat documentation.

2. Some integrations are wrappers around unofficial or scrape-fragile surfaces.
   The clearest example is Yahoo Finance, where the repo depends on `yfinance`, not an official Yahoo Finance API.

3. Contract drift already exists inside the repo.
   Crunchbase is the clearest current example:
   - [crunchbase.py](../../../src/solstein/connectors/financial/crunchbase.py) uses `X-cb-user-key` and `/searches/organizations`
   - [funding.py](../../../src/solstein/data/sources/funding.py) uses `Authorization: Bearer ...` and `/v4/organizations/{company_name}`
   These cannot both be treated as the same verified contract without a reconciliation pass.

4. Discoverability is uneven across providers.
   - strong `llms.txt` support confirmed: GitHub Docs, Exa Docs, Crunchbase Docs
   - `llms.txt` absent in first-pass checks: NewsAPI, Companies House developer site, `yfinance` docs
   - SEC actively rate-thresholded automated doc retrieval during this audit, which is itself an operational caveat

## Test And Validation Follow-Up

### External Contract Tests Needed

- Snapshot or fixture tests for normalized provider payloads
- auth-shape tests:
  - bearer vs header-key vs basic-auth
- rate-limit and retry tests
- empty-result and partial-result tests
- provider-version drift tests for the highest-risk surfaces

### Schema Gates Needed

- raw external payload schema
- normalized provider schema
- unified enrichment schema
- persisted fact schema

Each provider should fail at its own boundary, not later in scoring or reporting.

### Type Tightening Targets

- Python:
  - replace loose `dict[str, Any]` normalization results at the provider boundary with explicit pydantic models
  - add discriminated normalized result types for lookup providers and refresh facts
- TypeScript:
  - prioritize only the nodes where external payload misuse would silently corrupt downstream consumers
  - likely first candidates are future admin tooling, contract-fixture viewers, and exported JSON validation tooling with strict schema libraries such as `zod`

## Next Iteration Order

1. Secondary product and social connectors
2. decide whether `google_search` remains or is replaced with a verified provider path
3. convert the next external payload boundaries into strict TS contract fixtures
