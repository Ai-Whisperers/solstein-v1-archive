## The Audit Verdict

> `api/routers/auth.py` lines 57–60 contain the comment `# Demo: Accept any credentials` followed by code that constructs and returns a valid JWT for any username/password pair with zero verification. There is no bcrypt comparison, no argon2 call, no database lookup for stored credential hashes. The comment accurately describes the behaviour: it is a demo. It is in production.

## Problem Statement

The login endpoint performs no password verification. It receives a username and password, ignores them both except to embed the username in the JWT payload, and returns a signed token. Any actor with network access to the API can authenticate as any user.

## Impact

| Dimension | Effect |
|-----------|--------|
| **Security** | Full authentication bypass — any username/password pair grants access |
| **Compliance** | Violates OWASP A07:2021 (Identification and Authentication Failures) |
| **Data Exposure** | All company intelligence data is accessible to unauthenticated actors |

## Architectural Requirements

*What the system must satisfy. No implementation instructions. No code. Only what — never how.*

- **REQ-1**: Password verification must use an industry-standard adaptive hashing algorithm (bcrypt or argon2-cffi)
- **REQ-2**: Verification must be constant-time to prevent timing-based user enumeration attacks
- **REQ-3**: The login endpoint must return HTTP 401 for any invalid credential combination with a generic, non-differentiating error message
- **REQ-4**: The comment `# Demo: Accept any credentials` and all associated bypass logic must be entirely removed — not commented out
- **REQ-5**: Password hashing must occur at account creation time; the plaintext password must never be stored or logged
- **REQ-6**: Per-user salts must be generated by the hashing library and stored alongside the hash

## Acceptance Criteria

- [ ] Correct credentials return HTTP 200 with a valid JWT
- [ ] Wrong password returns HTTP 401 with a generic error message (no indication of which field was wrong)
- [ ] Unknown username returns HTTP 401 with the identical generic error message (no user enumeration)
- [ ] Response time for valid and invalid credentials is within 10% of each other
- [ ] Grep for `# Demo` and `Accept any credentials` returns zero results in the codebase

## Definition of Done

**Tests Required:**
- [ ] Unit test: hash comparison is invoked during login
- [ ] Unit test: login with wrong password → HTTP 401
- [ ] Unit test: login with unknown user → HTTP 401 with same message as wrong password
- [ ] Unit test: timing test — valid vs invalid credential response time parity

**Documentation Required:**
- [ ] Inline comment explaining which hashing algorithm is used and why

**Code Review Gate:**
- [ ] Reviewer confirms no plaintext password exists in any log statement, error message, or database write

## Notes

This story cannot safely ship without STORY-007 resolving the hardcoded database credentials. A real user store requires a trusted database connection. Implementing proper password hashing against a database reachable with `postgres:postgres` replaces one security failure with another.
